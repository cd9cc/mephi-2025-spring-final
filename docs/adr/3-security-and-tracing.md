# ADR-3. Безопасность (JWT) и сквозная трассировка запросов

## Контекст

ТЗ требует JWT-аутентификацию со сроком жизни токена 1 час, роли USER/ADMIN, самостоятельную проверку
токена каждым сервисом (Resource Server), корректные 401/403 и метод-уровневую безопасность. Booking
Service вызывает внутренние эндпойнты Hotel Service (`confirm-availability`, `release`), которые не должны
быть доступны пользователям. Критерии оценки также требуют корреляции запросов (traceId) в логах.

## Решение

### Токены

- Подпись HS256 общим секретом `security.jwt.secret` (переменная `JWT_SECRET`, ≥ 32 байт), проверка `iss`
  и `exp`. Внешний сервер авторизации и асимметричные ключи для учебного проекта избыточны.
- Выдаёт токены Booking Service (`JwtTokenService`, `NimbusJwtEncoder`):
    - пользовательский: `sub` - id пользователя, `username`, `role` (`USER`/`ADMIN`), срок - `security.jwt.ttl` (1h);
    - сервисный: `sub` - `booking-service`, `scope` - `internal`, срок 5 минут, выпускается на каждый вызов Hotel.
- Права: `role` -> `ROLE_USER`/`ROLE_ADMIN`, `scope` -> `SCOPE_internal`. Иерархия ролей `ADMIN > USER`:
  администратор может выполнять и пользовательские операции.

### Где проверяется доступ

1. Gateway - первый рубеж: без валидного токена запрос не уходит в сервисы (401). Открыты только
   `register`, `auth`, health. Роли на Gateway не проверяются.
2. Каждый сервис - Resource Server (`ResourceServerAutoConfiguration` в модуле `common`): заново проверяет
   подпись и срок, открыты только пути из `security.public-paths`.
3. Роли - `@PreAuthorize` на контроллерах:
    - USER: просмотр отелей и номеров, свои бронирования (чужие - 404, а не 403, чтобы не раскрывать их наличие);
    - ADMIN: CRUD отелей, номеров и пользователей, статистика загрузки;
    - `SCOPE_internal`: `confirm-availability`, `release` (пользовательский токен, даже ADMIN, - 403);
      `GET /api/rooms/recommend` доступен и USER, и сервисному токену (автоподбор номера).
4. Ответы 401/403 - в едином формате `ErrorResponse`, с заголовком `WWW-Authenticate: Bearer`.

Booking -> Hotel всегда использует сервисный токен, а не токен пользователя: внутренние шаги саги
выполняются от имени сервиса, а пользовательский токен не даёт к ним доступа.

### Общий код

Модуль `common` содержит Spring Boot auto-configuration для servlet-сервисов: Resource Server, глобальный
`@RestControllerAdvice`, фильтр трассировки, OpenAPI со схемой bearer. Зависимости фреймворка в `common` -
`compileOnly`, автоконфигурации включаются только в servlet-приложениях, поэтому Gateway (WebFlux)
использует из `common` лишь `ErrorResponse`, `TraceContext` и `JwtSupport`.

### Трассировка

- Заголовок `X-Trace-Id`: Gateway берёт его у клиента (если значение корректно - `[A-Za-z0-9-]{8,64}`,
  защита логов от инъекций) или генерирует, передаёт в сервис и возвращает клиенту.
- Сервисы кладут traceId в MDC (`TraceIdFilter`, до Spring Security), Booking передаёт его в Hotel
  (`TracePropagationInterceptor`), `ErrorResponse.traceId` совпадает с заголовком.
- Шаги саги дополнительно помечены MDC-ключом `bookingId` в обоих сервисах (ADR-2).
- Формат логов: в Docker - JSON в формате ECS (`LOGGING_STRUCTURED_FORMAT_CONSOLE=ecs`), MDC-ключи
  `traceId`, `bookingId` становятся полями записи; при локальном запуске - текст с префиксом
  `[traceId,bookingId]` (`logging.pattern.correlation`). Gateway (WebFlux) выставляет MDC только на время
  записи access-лога, так как реактивный конвейер меняет потоки.

Готовые решения (Micrometer Tracing + Zipkin) отклонены: требуют отдельной инфраструктуры, а
собственный заголовок прозрачно проверяется тестами.

## Последствия

- Компрометация общего секрета позволяет выпускать токены; в продакшене следует перейти на RS256 и
  выдачу токенов отдельным сервером авторизации.
- Отозвать выданный токен до истечения часа нельзя (stateless). Удалённый пользователь с действующим
  токеном получит 404 при создании бронирования.
- H2 console отключена: с Resource Server она требовала бы отдельной настройки безопасности.
