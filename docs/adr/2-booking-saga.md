# ADR-2. Сага бронирования, идемпотентность и устойчивость вызовов

## Контекст

Бронирование затрагивает две базы: `bookings` в Booking Service и `room_reservations` в Hotel Service.
Глобальные распределённые транзакции по ТЗ не используются. Нужно: двухшаговое подтверждение,
компенсация при сбое, идемпотентность при повторах и отсутствие двойных бронирований при конкуренции.

## Решение

### Шаги саги (оркестрация в Booking Service, `BookingSaga`)

1. Локальная транзакция: бронирование сохраняется в статусе `PENDING`.
2. `POST /api/rooms/{id}/confirm-availability` - Hotel Service блокирует слот (`room_reservations.status = ACTIVE`)
   и увеличивает `times_booked`.
3. Результат:
    - успех -> локальная транзакция `PENDING -> CONFIRMED`;
    - отказ (409/404: номер занят, выведен из эксплуатации, не существует) -> при автоподборе пробуется следующий
      рекомендованный номер (до `booking.auto-select-max-rooms`), иначе `PENDING -> CANCELLED (ROOM_UNAVAILABLE)`,
      компенсация не нужна - блокировка не создавалась;
    - сбой (тайм-аут, 5xx, разомкнутый circuit breaker) -> результат в Hotel неизвестен, поэтому выполняется
      компенсация `POST /api/rooms/{id}/release` и `PENDING -> CANCELLED (HOTEL_UNAVAILABLE)`.

Удалённые вызовы выполняются между локальными транзакциями, никогда внутри них (`BookingStateManager`).

### Зависшие PENDING

Сага выполняется синхронно в потоке запроса. Если она прервалась после фиксации `PENDING` (непредвиденная
ошибка, остановка экземпляра), бронирование нельзя ни подтвердить, ни отменить, а повтор запроса возвращает
его в `PENDING`. Это исправляет `PendingBookingRecovery`: раз в `booking.pending-recovery-interval` (1m) он
находит бронирования `PENDING`, которые не менялись дольше `booking.pending-timeout` (5m). Тайм-аут с запасом
больше самого долгого прогона саги: около 10s на номер со всеми повторами, при этом `changeRoom` обновляет
`updated_at`. Для каждого такого бронирования:

1. локальная транзакция `PENDING -> CANCELLED (PROCESSING_TIMEOUT)`, только если статус всё ещё `PENDING`;
   конфликт с шагом саги ловит оптимистическая блокировка (`version`), и бронирование проверяется
   на следующем прогоне;
2. компенсация `release` в Hotel.

Отмена идёт раньше `release`. Поэтому сага, которая ещё работает, после этого не сможет подтвердить
бронирование: `confirm` получит конфликт и сама снимет свою блокировку. Повтор запроса с тем же `requestId`
получает 503, как при `HOTEL_UNAVAILABLE`.

Отмена подтверждённого бронирования пользователем: сначала `release` в Hotel, затем `CONFIRMED -> CANCELLED`.
Если Hotel недоступен, бронирование остаётся `CONFIRMED` (503) - состояния сервисов не расходятся.

### Идемпотентность

- Клиент передаёт `requestId` в `POST /booking`; `bookings.request_id` уникален. Повтор возвращает то же
  бронирование (или ту же ошибку для отменённого сагой), повторных вызовов Hotel не происходит. Гонка двух
  одинаковых запросов разрешается уникальным ограничением.
- Booking -> Hotel: `requestId = booking-{bookingId}-room-{roomId}`, детерминирован, поэтому HTTP-повторы
  распознаются Hotel Service как дубликаты (`room_reservations.request_id` уникален) и не меняют доступность.
- Поздний дубликат `confirm-availability` после `release` возвращает блокировку в статусе `RELEASED` и не
  занимает номер повторно; Booking трактует это как отказ.
- `release` идемпотентен: повторный вызов или вызов без блокировки - no-op.

### Конкуренция

Hotel Service берёт пессимистическую блокировку строки номера (`SELECT ... FOR UPDATE`) перед проверкой
пересечений. Конкурентные попытки занять один номер на пересекающиеся даты выполняются последовательно:
успешна ровно одна, остальные получают 409.

### Устойчивость вызовов (Resilience4j)

- Тайм-ауты одной попытки: connect 1s, read 2s (`hotel-client.*`).
- HTTP-клиент - JDK HttpClient, выбранный явно: Apache HttpClient (есть в classpath через Eureka client)
  сам повторяет ответы 503, в том числе POST, и умножал бы число попыток Resilience4j (проверяется
  `HttpHotelClientTest`).
- Retry: 3 попытки, экспоненциальная задержка 200ms × 2; повторяются только временные сбои
  (`HotelUnavailableException`: тайм-аут, ошибка соединения, 5xx). 4xx не повторяются.
- Circuit breaker: окно 10 вызовов, порог 50% ошибок, минимум 5 вызовов, открыт 10s.

### Корреляция

Все записи журнала саги содержат `bookingId` (в тексте и в MDC-ключе `bookingId`);
`requestId` Hotel-вызовов включает `bookingId`, поэтому шаги прослеживаются и в логах Hotel Service.

## Последствия

- Если компенсация сама не удалась (Hotel недоступен), блокировка слота может остаться - это логируется
  на уровне ERROR. Сверка уже отменённых бронирований с блокировками Hotel для учебного проекта не
  реализуется; фоновая задача обрабатывает только зависшие `PENDING`.
- `times_booked` уменьшается при `release`, то есть отражает действующие бронирования.
